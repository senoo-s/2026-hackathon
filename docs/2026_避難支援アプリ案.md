# 避難支援アプリ案(Built with Claude: Japan 2026)

打ち合わせで出た「スマホで災害時にオフラインで避難経路を確認できるアプリ」を具体化した案。

## コンセプト
平時にClaudeが対話で聞き取り、一人ひとりに合わせた「避難パック」を作ってスマホに保存する。災害時は通信できればClaudeが判断を支援し、通信できなくても保存済みのパックで案内を続ける。

## 課題意識
- 自治体のハザードマップや避難情報は、誰にでも同じ内容で、自分の状況に当てはめにくい
- 災害直後は回線が混雑し、クラウドのAIに頼れない場面がある
- 出先(通勤先・旅行先)では、そもそも土地勘がない

## 仕組み
### 平時(オンライン)
- Claudeが対話で聞き取る項目: 自宅・職場・通勤経路・よく行く場所、同居家族、移動手段など
- 公開されているハザードマップの情報から、災害の種類ごとの避難先・経路・持ち出しチェックリストを生成し、端末に保存する
- 旅行先など新しいエリアのパックも、通信できるうちに生成・保存しておく

### 災害時(二段構え)
- **初動(オフライン)**: 保存済みのパックからルールベースで即時に案内する(高台へ、建物から離れる、など)。命に直結する判断は通信に頼らない
- **落ち着いた後(オンライン)**: 通信が戻ったらClaudeが状況に応じて支援する。帰宅困難時にどこで過ごすか、連絡の順番、交通の再開状況など

### 道路の被害への対応
事前に作った経路は災害時の道路の被害(地割れ・倒壊・車の事故など)を知らないため、「その道が通れない」ことを前提にする。
- **複数の経路・避難先を用意する**: 1つに絞らない。狭い路地・古い建物やブロック塀の多い道・川沿い・崖の近く・アンダーパスを避け、幅の広い道を優先する。土砂災害警戒区域・液状化マップ・緊急輸送道路など公開データを判断材料にする
- **「この道は通れない」ボタン**: 押した区間を除いて、端末内のオフライン地図で経路を引き直す。AIは使わず、オフラインで動く
- **写真での判断は控えめに**: 通信できるときに道路の写真をClaudeに見せる場合も、「通れます」とは判断させない。「近づかない」「別の道を選ぶ」など安全側の助言と代わりの経路の提示に留める
- **徒歩避難を基本にする**: 車は渋滞や事故の原因になるため勧めない。高齢者・要介護者がいる場合などは例外として扱う

## 前例と差別化
- オフラインで見られる地図アプリは自治体アプリですでに一般的(甲府市・大分県・中央区など)で、ここ自体は差別化にならない
- マイ・タイムライン作成ツール(国交省、射水市、石岡市など)は入力に応じた定型判定で、生成AIは使っていない
- 最も近い前例はハッカソン作品「Sonae」(AMD Developer Hackathon、2026年5月)。個人別の避難計画をAIが作るが、エッジに置いた大型GPUでローカルLLMを動かす前提で、スマホ単体の構成ではない
- 本案の違い: 災害時のリアルタイムAIに依存しない設計(平時に生成、初動はオフライン、通信が戻ればClaude)と、日本のハザードデータとの連携
- 想定される質問「汎用チャット(ChatGPT等)で相談すれば足りるのでは」への回答: ハザードデータとの連携と、オフライン用のパッケージ化は汎用チャットではできない

## リスク・配慮
- 「最終判断は自治体の避難情報に従う」旨の免責を表示する
- 住所や家族構成は端末内だけに保存し、サーバーには残さない
- 避難行動の判断そのものを代行せず、公開情報の整理・提示に留める

## プロトタイプで作る範囲
前提: ハッカソンではプロトタイプが作れれば十分。作るものを絞り、それ以外は「将来構想」として説明だけにする。

### 作るもの
- **共通パック**: 1つの市区町村分。Claude Codeでローカルから生成したJSONファイルとして持たせる(実行時の生成サーバーは不要)
- **聞き取りと個人調整**: Claudeとの対話で聞き取り、共通パックを元に個人向けに調整する。共通パックは即座に表示し、Claudeの調整は後から反映する
- **オフライン表示**: PWA(Service Worker)で、機内モードでも案内が続くようにする
- **道路の被害への対応**: 複数経路の用意と、「この道は通れない」ボタンによる経路の引き直し

### 動かす場所
成果物の形式(応募後の案内待ち)を見て決める。
- デモ動画で足りる場合: ローカル(localhost)で動かすだけ。サーバーは不要
- 審査員が触る必要がある場合: Cloudflare Pages(アプリ本体と共通パックの静的配信)とWorkers(APIキーを隠す中継の1ファイル)を足す。半日程度の作業で、無料枠に収まる

### デモシナリオ
1. Claudeとの対話で聞き取り、避難パックを生成する
2. 通信ありの状態で、現在地に応じてClaudeが案内する
3. 機内モードに切り替えても、保存済みのパックで案内が続く
4. 「この道は通れない」ボタンを押すと、オフラインのまま別の経路に切り替わる

## 将来構想(説明のみ・作らない)
審査員の質問に答えるための材料。本番化するならこうする、という位置づけ。

### ネイティブアプリ化
- PWAはバックグラウンドで位置を検知できないため、新しいエリアに入ったときの自動の先回り生成はネイティブ化で実現する(プロトタイプでは旅行前に手動でエリアを保存する方式)
- ストア登録料: Apple年$99、Google初回$25

### 通行情報の共有
- 他の利用者が報告した「通れない道」を共有する。通信と投稿内容の管理(誤情報・いたずら対策)が必要になるため、本番化の段階で検討する

### 通信量・電池
位置の判定を端末内で済ませ、通信は新しいエリアのパックを作るときだけにすれば、通信量も電池消費も小さく抑えられる。位置情報をサーバーに送り続けないので、個人情報の面でも有利。
- 通信が発生するのは初回の聞き取り(1回)、新しいエリアに入ったとき(遠出で月に数回程度)、保存済みエリアの更新(月1回程度)だけ。テキストのみなら月1MB未満の見込み(想定ベースの試算で、実測ではない)
- 一度保存したエリアは再生成しない。地図データはWi-Fi接続時のみ取得する設定を用意する
- 常時GPSで追跡せず、OSの「大きな移動」検知(iOSのSignificant Location Change、AndroidのGeofencing)に任せる。エリア判定は数百m〜数km、または市区町村単位の粗さにする
- パック更新や地図取得は、充電中またはWi-Fi接続時にOSのバックグラウンド処理(BackgroundTasks、WorkManager)で行う
- 高精度GPSは、警報を受けたときかアプリを開いたときだけ使う
- 先回り生成はオフにできるようにする(登録地点だけを持つ軽量モード)
- 災害時の画面は方角と距離の表示を基本にする(停電で充電できない状況を想定)

### キャッシュとコスト
- 共通部分(エリアごとのハザード情報・避難先・災害種別の注意点)は事前に一括生成してキャッシュし、個人部分(家族構成・移動手段など)だけを都度調整する二層構成
- API費用が利用者数ではなくエリア数に比例する。事前に人の目で内容を確認でき、生成AIの誤りへの対策になる。自治体単位でダウンロードでき、オフライン対応と相性がよい
- 現在地からの経路は端末側のオフライン地図で計算する。避難所の変更やハザードマップ改訂時にキャッシュを作り直す
- 費用の目安(概算): 中継サーバーは無料枠〜月数千円。主な費用はClaude APIの利用料(パック1回の生成で数円〜数十円程度)。社会実装では自治体にAPI費用を負担してもらう形が考えられる

### 応答速度
- 応答はストリーミングで返し、生成された部分から表示する
- モデルを使い分ける: キャッシュの一括生成は品質優先(Opus/Sonnet)、個人調整や災害時の応答は速度優先(Haiku)
- プロンプトキャッシュで共通の前提部分の処理を省く(速度向上と料金削減)
- 出力は決まった形式(JSONなど)で要点のみとし、整形はアプリ側で行う
- 個人調整は登録時に済ませて端末に保存し、災害時の初動ではClaudeを呼ばない

### サーバー障害への備え
オフライン優先の設計のため、サーバーが落ちても命に関わる初動の案内は止まらない。
- **落ちたときの表示**: 保存済みのパックで案内を続け、「相談機能は一時停止中」と短く表示する。タイムアウトを短めにし、フリーズさせない
- **一斉再接続の防止**: 大地震直後の同時再試行に備え、指数バックオフ＋端末ごとのランダムなずれで再試行間隔を延ばす。利用者ごとの回数制限も入れる
- **共通パックはCDNで静的配信**: 中継サーバーが止まってもダウンロードは続けられる
- **Claudeの予備経路**: Anthropic APIに加え、AWS Bedrock/Google Cloud Vertex AIに切り替えられるようにする
- **被災地のデータセンターに依存しない**: Cloudflare Workersのような世界中の拠点で動く構成にする
- **災害前の更新通知**: 大雨・台風の予報が出た時点でパックの更新を促し、負荷が集中する前に済ませてもらう
